## Account self-service (Task M2.3, design in `docs/design/accounts.md`)

- `PATCH /api/auth/me` changes the display name only (strict schema `updateMeInput`; username and admin flag cannot be set). `POST /api/auth/password` now ends the user's other sessions and keeps the current one (`endUserSessions` in `auth/session.ts`), and is limited to 5 tries a minute per user. Both refuse API tokens (`rejectTokenScope`).
- Disabled users (`users.disabled_at`, set directly for now; the admin routes come in M2.4) are not resolved anywhere: the session cookie, the in-process MCP call (`sessionMiddleware`) and `ApiTokenService.verify` (so `/mcp` answers 401) all refuse them. Login answers 403 "This account is disabled" only after the correct password.
- `lib/rate-limit.ts` replaces the private login limiter: expired keys are pruned on write and the map is capped at 10 000 keys; Retry-After on 429; a second login budget of 30 failures per 15 minutes per username, whatever the address.
- **`TRUST_PROXY`** (default off, `.env.example`, README table): the caller key is the socket address. `X-Forwarded-For` (rightmost entry) is read only when it is `1`; while off, the first request carrying the header logs one warning. Before this, rotating the header bypassed the login limit.
- Tests: `apps/server/test/account.test.ts`. The reset budget is wired in M2.5 (below).

## User administration (Task M2.4, design in `docs/design/accounts.md`)

- `/api/admin/users` (admin browser sessions only; `requireAdmin` also rejects API tokens, and `mcp/api.ts` has no pattern for it, locked by `isAllowed` + a test over `app.routes`): `GET /` list, `GET /:id/owned-campaigns`, `POST /:id/reset-link` (201 `{ url, expiresAt }`, url is `<PUBLIC_URL>/reset#<token>`, shown once, only the hash is stored, a newer link supersedes older ones, optional `revokeTokens`), `PATCH /:id` (`disabled`, `isAdmin`), `POST /:id/delete` (204).
- The acting admin's own password (`currentPassword`) is required for reset-link, delete, grant, revoke, disable and enabling an ADMIN account (wrong: 403, 5 tries a minute per admin, then 429). Enabling a non-admin needs none. A missing password for an admin target is 400 "Enter your password to enable an admin account" (checked in the service transaction, as the zod schema cannot know the target). The limiter counts the attempt before the password check is awaited and gives back only that one attempt on success (`RateLimiter.give`), so concurrent wrong guesses cannot all pass the budget check.
- Delete/transfer (M2.8 prep): a transfer to a disabled member is rejected with 400 (the whole plan rolls back); `GET /:id/owned-campaigns` members carry `disabled: boolean` so the UI can mark or skip them.
- Last-admin rule (`assertNotLastAdmin`, counts other enabled admins) holds for revoke, disable and delete; an admin cannot disable or delete themselves, and can demote themselves only while another enabled admin exists. Every write re-reads the acting admin as the first statement of one synchronous transaction, so an admin demoted a moment earlier is refused (403). Disabling ends the user's sessions and revokes their API tokens and open reset links.
- Delete (D5 option C): the request must give a choice for every campaign the user owns, or it is rejected with 400 naming the missing ones. Transfer goes to a current member (becomes `dm`); archive needs a co-DM; a solo campaign cannot be orphaned (disable the user instead). Open invites the user made are revoked. Homebrew sources shared with campaigns or the instance go to the acting admin (a campaign's own source goes to its new owner); private sources and user templates stay ownerless and invisible (readers already treat a null owner as "not mine", no crash). Archived campaigns keep their co-DM and have no `dm` row.
- Audit: one JSON log line per event (`lib/audit.ts`): `reset_link.created`, `reset_link.superseded`, `user.disabled`, `user.enabled`, `admin.granted`, `admin.revoked`, `user.deleted`, with actor, target, `targetIsAdmin`, ip; never tokens, links or passwords.
- `createResetLink(db, userId, createdBy | null, baseUrl)` in `services/users.ts` is the shared function for the CLI (M2.6). Redeem is M2.5 (below); users page is M2.8.
- Tests: `apps/server/test/admin.test.ts`.

## Password reset by link (Task M2.5, design 4.1)

- `GET /api/auth/reset/:token` returns `{ username, displayName, expiresAt }` for a live link and never consumes it. `POST /api/auth/reset/:token` with `{ newPassword }` (strict `redeemResetInput`) sets the password, ends all of the user's sessions and the session row of the incoming cookie, and signs in with a fresh session. No auth requirement; behind `originCheck` like every `/api/*` route; not in the MCP allowlist (tested). Responses carry `Cache-Control: no-store`.
- Order (normative, tested): body validation first (weak password: 400, even with a garbage token); read-only liveness lookup; argon2 only for a live token; one synchronous transaction whose conditional `UPDATE ... used_at` must change exactly 1 row (single use under concurrent POSTs: one 200, the rest 404; a user disabled meanwhile rolls everything back, link not burned); other open links of the user are closed.
- Unknown, expired, used, superseded and disabled-user links all answer `404 { error: 'This reset link is not valid' }` with identical headers. Non-live lookups (GET and POST) count against a budget of 30 per 10 minutes per caller key (`createClientKey`), then 429 with `Retry-After`; a live token is never refused or counted, so prefetching GETs cannot burn it.
- `purgeOldResets` (expired and used rows) runs at start-up beside `purgeExpiredSessions`. Audit event `password.reset` (target id, ip); no token is logged. As design T5 says, the token is in the API path, so a reverse proxy's access log can hold a live token until used.
- Tests: `apps/server/test/reset.test.ts`. Reset page: M2.9 (below).

## Reset page (Task M2.9, design in `docs/design/admin-users-ui.md` section 10)

- `/reset#<token>` (`apps/web/src/app/auth/reset.ts`, lazy, top-level and outside `authGuard`; deviation from `/reset/:token` logged in PLAN.md). The token is read from `location.hash` in the constructor and removed with `history.replaceState` before any request; it lives in a private non-signal field, never in storage, router state, logs, the title or an error message, and is cleared once the link is dead or used. - Flow: shape check (43 base64url characters, no request otherwise) -> `GET /api/auth/reset/:token` (whose account, expiry) -> two password fields (shared `passwordSchema`, match check, `autocomplete="new-password"`, hidden username field) -> `POST` -> `auth.refresh()` -> `/campaigns` with `replaceUrl`.

On POST: 400 inline under the new-password field, 429 inline via `requestError`, network inline. If `refresh()` fails after the password changed, a message with a link to `/login`.

## Backup service (Task M3.2, design in `docs/design/backup.md`)

- **Code** (no routes, no CLI subcommands, no timer yet: those are M3.3 to M3.5): `src/services/backups.ts` (`BackupService`: `create({ actor, trigger })`, `list()`, `prune(keep, origin)`, `status()`, `isRunning()`, `openForDownload(name, actor)`; the four database-specific functions of design 15: `snapshotDatabase`, `readMigrationLevel`, `prepareRestoredDatabase`, `probeStopped`; and the restore building blocks `readBackup` (verify or extract), `compareMigrationRows`, `referenceSchema`/`compareSchema`, `carryOverRestrictions`), `src/services/backup-zip.ts` (writer, bounded reader, manifest and checksum schemas), `src/services/backup-fs.ts` (`BACKUP_DIR` validation, the lock file), `src/lib/ops-log.ts` (`restore-log.jsonl`), `src/lib/version.ts` (`appVersion()`; `scripts/build.mjs` injects `__APP_VERSION__` with an esbuild `define`), `openAppDbForRestore` in `src/db/index.ts`, `BACKUP_KEEP` and `BACKUP_DIR` in `src/config.ts`.
- **A backup** is `backup-<UTC timestamp>.zip` in `BACKUP_DIR` (default `DATA_DIR/backups`, mode 0700; zips 0600 whatever the umask): `manifest.json` first, `app.sqlite` (online backup API, converted to one self-contained file, `integrity_check` ok), `uploads/<id>[.thumb]` taken after the snapshot, `checksums.json` last. Written to `.partial-*`, **verified by the same reader restore uses**, then published with a no-clobber `link()` and an fsynced directory; a failed verify, a full disk or a kill leaves earlier backups alone and prunes nothing. One backup at a time (in-process flag plus `backups/.lock`, stale after 2 minutes; takeover by rename, with a microsecond window between the rename and the put-back of a live lock that the in-process flag covers inside one process). Refused while `DATA_DIR/.restore-in-progress` exists.
- **Retention** is exactly the design 11 rule: API-created backups younger than 7 days are protected and uncounted; everything else is ranked by the timestamp in the name and the newest `BACKUP_KEEP` kept; an API-started prune only deletes backups aged 7 days or more; an API create is refused (`BackupError` code `api-cap`, HTTP 409 for M3.4) at `3 x keep` young API backups. `trigger` (`api`, `cli`, `scheduler`) is a required argument of `create`, written into the manifest, never read from input; unreadable, foreign or corrupt files are classed `api`.
- **The reader is not fflate's `Unzip`.** Measured: fflate's streaming reader finds the end of an entry by scanning for `PK\x07\x08`/`PK\x01\x02`, and deflate emits incompressible data (every JPEG, PNG, WebP) as stored blocks, so any upload containing those bytes was cut short (`unexpected EOF`); the design's experiment only used compressible test data. `backup-zip.ts` reads the central directory with positional reads and inflates with `node:zlib` (bounded: 64 KiB pieces, caps and ratio limits while inflating). It checks `compression === 8` for every entry before anything is read, the exact name allowlist, that the entries tile the file with no gap and no byte after `checksums.json`, an end record with comment length 0, every crc and every sha256. The zip layout is unchanged (standard zip; `unzip -t` and Python `zipfile` read it). The writer still uses fflate `ZipDeflate` only (level 1, level 6 for the database), but writes the central directory itself with zip64 records, because `Zip.end()` wraps 32-bit offsets and the entry count (an archive over 4 GiB or with over 65,535 entries would be corrupt).
- **Restore building blocks** (the CLI in M3.3 calls them): `readBackup(zip, { extractTo, maxTotalBytes })` streams into a staging directory under all design 9 limits (entry count, per-kind sizes, a lying manifest can only lower the database cap, ratio 200:1 after 1 MiB and, for the database, 200:1 after 4 MiB (50:1 until page history, N1.2), total cap, and the deflate stream must end exactly at the entry's compressed size); `prepareRestoredDatabase(staged, { keepTokens, live, carryRestrictions, stagedUploadsDir })` does design 8 step 3 (read-only open with `trusted_schema = OFF`, `cell_size_check = ON`, `query_only`; the staged `__drizzle_migrations` rows against the journal; the `sqlite_master` allowlist against a `:memory:` database of the same journal prefix BEFORE anything is migrated; integrity and foreign key checks; migration with `openAppDbForRestore`; sessions and resets deleted, tokens and invites revoked, live restrictions carried over; `journal_mode = DELETE`; fsync and sha256) and returns a report (no secrets); `probeStopped` is the exclusive-lock probe. The marker, staging directory, swap, rollback and the report text are M3.3.
- **Note for M3.3:** `__drizzle_migrations.id` is NULL in SQLite (drizzle declares it SERIAL), so rows are read `order by rowid`. The schema allowlist is stable for every historical migration level 0000 to 0006 (test `every historical migration level upgrades to a schema equal to a fresh one`), so the M3.3 blocker test is already satisfied at the service level; M3.3 repeats it through the CLI.
- **Tests** (about 140 new: `test/backup-zip.test.ts`, `test/backups.test.ts`, `test/backup-restore.test.ts`, helpers `backup-helpers.ts` and `zip-builder.ts`, fixture `fixtures/backup-kill.ts`): consistency under writes (same connection, another connection, another process), round trip equality, adversarial bytes, the gate, zip-slip and layout, limits, zip64 (a crafted sparse directory with offsets above 4 GiB, the writer's extra-field encoding, a written archive), memory bound by chunk instrumentation on about 80 MB of uploads (`CN_SLOW_TESTS=1`: 520 MB with RSS and event-loop checks and 66,000 entries), order guarantee, locking, prune and the flood scenarios, `BACKUP_DIR` validation, disk and ENOSPC, kill during creation, planted schema, forged migration rows, carry-over, the lock probe against a real second process.
- **Manual extraction note (for the M3.6 guide):** Info-ZIP `unzip` 6.0 reports its zip-bomb heuristic ("overlapped components") on a backup with entries beyond 4 GiB; use `UNZIP_DISABLE_ZIPBOMB_DETECTION=TRUE unzip`, 7-Zip or Python `zipfile` to open such a file by hand. The archive is valid (7-Zip, Python and the app's own reader accept it).
- **Residuals:** a database that compresses better than 50:1 after its first 4 MiB of output (for example one filled with `zeroblob`) fails the verify pass by design, so such a backup is refused rather than made (a fresh migrated database measured 48.8:1 at 1 MiB, close to the limit, which is why the database's rule starts at 4 MiB). The memory test forces a collection before it samples (fflate's output buffers are garbage at once but V8 frees them late: without collecting, peak RSS growth measured 60 to 74 MiB, with it 9 to 12 MiB). Backups are CPU-bound by fflate (about 26 MB/s on this machine for incompressible uploads, see PLAN.md).

## Backup and restore commands (Task M3.3, design 7, 8, 10, 18, 19)

- **Commands**: `node dist/admin.mjs backup` (stdout = the path of the zip; `BackupService.create` with trigger `cli`, 2000-page copy steps, `BACKUP_KEEP` prune as an unrestricted `cli` prune; the starvation warning and the audit JSON go to stderr; `restore-log.jsonl` gets `backup.created`) and `restore <file> [--check] [--yes] [--keep-tokens] [--no-carry-restrictions]`. Code: `src/cli/run.ts` (`runAdmin(argv, io)`: the process-free entry the tests call; refuses every command but `restore` while the marker exists), `src/cli/admin-core.ts` (`SUBCOMMANDS`; entries may be async and may set `needsDb: false`, which skips the generic `openAppDb`), `src/cli/errors.ts` (`EXIT`, `CliError`), `src/cli/backup.ts`, `src/cli/restore.ts` (the whole of design 8), `src/lib/restore-marker.ts` (marker type, the strict names pattern, the refusal text, `refuseWhileRestoring`), `openAppDbNoMigrate` in `src/db/index.ts` (a CLI backup never migrates the live database). `admin.ts` is now only the process wiring.
- **Exit codes**: 0 ok; 1 unknown user, 2 disabled user, 3 not found, 64 usage, 65 invalid backup, 66 newer backup, 67 different migration history, 69 server running, 70 failed, 71 rolled back, 72 cancelled, 74 disk full, 75 restore in progress, 76 backup already running, 77 rollback failed. stdout carries only the result (a path, the link or the restore report); the plan, hints and audit lines go to stderr.
- **Restore, in short** (read `src/cli/restore.ts` top to bottom; every step is `mark(next)` then act then hook): parse and fail early (`--keep-tokens` needs `--yes`; no terminal and no `--yes` is exit 64) → layout checks (`DATA_DIR` and `uploads/` not symlinks, `uploads/` same file system) → read the marker (a `rollingBack` marker is only ever continued as a rollback, whatever file is given) → preflight (sha256 of the zip, central directory and manifest, the early advisory migration check, free space `max(3 x zip, declared) + 64 MiB`) → exclusive run lock (`.restore.lock`, an exclusive SQLite lock) → marker created (no-clobber `link()` of a finished file, so it is never empty or torn) → `probeStopped` (refuses when the server runs; a damaged live database only skips the carry-over) → stage into `.restore-<ts>/` (`readBackup` into an empty dir, `prepareRestoredDatabase` with the probe as the live window) → marker `staged` with the sha256 and the report → confirm → pre-swap check (probe alive, same dev/ino) → probe closed → swap: `preRestoreDir`, `moveLive` (the move list is written before the first move), `moveUploads`, `install` (racer sweep to `pre-restore-<ts>/racer-<n>-*`, then no-clobber `link()`), `indexDelete`, `finish` (restore.completed, marker removed, report). A racer that stays, or a `-wal`/`-shm` that appears, runs the five-step rollback (`removeInstalled`, `uploadsBack`, `liveBack`, `deleteStaging`, `finalize`); if the rollback cannot finish the marker stays with `rollingBack.failed` and the manual instructions are printed (exit 77).
- **`main.ts`** checks the marker at the very top (before `ensureDataDirs` and `openIndexDb`) and again after `openAppDb` (it closes both databases first), prints what to do (run the same command again, or abort by hand) and exits 1; with `restart: unless-stopped` that is a harmless crash loop. An unreadable marker stops it too.
- **Restore drill** (`apps/server/scripts/restore-drill.mjs`): starts a server on a temp directory, sets it up over HTTP (admin, campaign, page, an image), takes a CLI backup while the server runs, writes a page after it, stops the server, wipes the data directory, runs `restore --check` and `restore --yes`, starts the server again and checks over HTTP: old session gone, login with the old password, campaign, page, image byte for byte, search finds the restored page and not the one written after the backup. `--mode dist` (default; the bundle the image runs) or `--mode src` (tsx). **For M5.2 (CI)**: add one job step after the build, `pnpm --filter @cn/server build && pnpm --filter @cn/server drill` (also `pnpm drill` from the root); exit 0 = passed, the log is on stderr; it needs no 5etools data, no network and no browser, takes about 15 s and writes only to a temp directory. The vitest wrapper `test/restore-drill.test.ts` runs the same script on the sources (and on `dist/` when a build exists), so the normal gate already exercises it.
- **Tests**: `schema-allowlist.test.ts` (the M3.3 blocker, 22 tests: genuine databases of every historical level 0000 to 0006 equal to a fresh one by the allowlist, by `prepareRestoredDatabase` and by the server's own upgrade path; planted trigger, view, extra table, extra index and `sqlite_stat1` refused at every level; a guard that fails when a new migration uses DDL that can make the allowlist unstable until a human reviews it), `restore-cli.test.ts` (wiped and live instances, stale WAL, damaged live database, refusals, races and rollback, carry-over, `restore-log.jsonl`, secrets, ownership, hostile and corrupt zips, the migration levels, `backup`), `restore-crash.test.ts` (a child process is SIGKILLed at every one of the 25 or so points of the forward path and of the rollback, then the command is run again; plus the server start guard), `restore-drill.test.ts`. Mutation checks of the key guards are in PLAN.md.
- **Review round 1 (R1 to R6 and the Code Reviewer items)**: the probe no longer fails open: only `SQLITE_CORRUPT*`/`SQLITE_NOTADB` count as a damaged live database, `SQLITE_BUSY*`/`SQLITE_LOCKED*` mean the server runs (69), and any other error (permissions, a read-only mount, a lock error) refuses with exit 78 "Cannot lock app.sqlite (<code>), refusing". As root the restore uses `lchown`, never walks the old (untrusted) uploads tree, and the ops log opens with `O_NOFOLLOW` and `fchmod`; the marker is shape-checked (`readRestoreMarker`: move-list names must be the three database names, hashes 64 hex, rollback step known, user present) and an invalid one is "unreadable" and never acted on. The marker is read again under `.restore.lock`; the probe is released before any swap, resumed or not; a symlinked or non-regular `app.sqlite`, `-wal` or `-shm` is refused before the marker exists. A canonical `sqlite_stat1`/`sqlite_stat4` (from `ANALYZE`) is tolerated and dropped from the staged copy before migration; any other extra object is refused with a message that names it (control characters neutralised) and says what to do. If hard links are not supported the install falls back to an exclusive copy (`COPYFILE_EXCL`, fsync). Stale `.restore-in-progress.tmp-*` files and `.restore-check-*` folders older than an hour are swept. Tests: `test/restore-review.test.ts`.
- **Known limits**: the lock probe relies on POSIX file locks (network file systems and some bind mounts are unsupported for restore, design 21); a hand-run script that opens the database without `main.ts` can still interleave (design 7.1 point 4). A hot WAL left by a crashed server is merged into the old file by SQLite when the probe lets go of it, so the pre-restore copy is one self-contained `app.sqlite` (see PLAN.md).

## Admin backup endpoints (Task M3.4 endpoints; the page is the Frontend Developer's half; design 10, 11, 13, 14, 19)

- **Review round 1 hardening**: download open uses `O_NOFOLLOW | O_NONBLOCK` and refuses `nlink !== 1` (FIFO and hard link tests); the body is a pull-based web stream with an idle watchdog (`downloadLimits.idleMs`, 60 s: a reader that drains nothing is destroyed, freeing slot and lease; no total cap, a reading client may take as long as it needs); the slot check (429) runs BEFORE the ticket is redeemed, so a 429 burns nothing (it only tells an already-authenticated admin that downloads are busy; the ticket still needs the right admin, session and name); any synchronous throw while opening the stream frees slot and lease; `HEAD` on the download is 405 (no ticket redeemed, no `backup.downloaded`); `ip` (client key, honours `TRUST_PROXY`) is on `backup.ticket_issued`, `backup.ticket_denied`, `backup.downloaded`, `backup.created` and `backup.failed`.
- **Small deviation from design 13 ("the list reads no zip")**: the list reads each file's bounded manifest head once (cached by name+size) for app version, migration level and counts. Flagged in PLAN.md and amended in design 13.
- **Small changes to the M3.2 service** (needed by the endpoints, behaviour of the CLI unchanged): `list()` entries carry the manifest facts (`detail`: app version, migration tag, counts, missing uploads) from the same bounded first-entry read that classifies the trigger (one read per name+size, cached); `status()` also returns `lastErrorCode` (a stable code, so routes show a fixed sentence and never the raw `lastError` text, which can hold paths); `assertApiCreateAllowed()` is the API cap check extracted from `create()` so the route can answer 409 before it answers 202.
- **Async decision (design 13)**: `POST` answers 202 and the page polls `GET`. The route checks the API cap, then (no `await` in between) `isRunning()`, then starts `create()` without awaiting it, and waits at most 300 ms for an early refusal (another process holds the lock, restore marker, disk preflight) so those still come back as 409/507. `name` can be `null` until the backup holds its lock.
- **Ticket**: 32 random bytes (43 base64url chars), stored as sha256, bound to admin id + session id + file name, 60 s, single use. The first presentation removes it even when the binding does not match (a stolen ticket is burnt). Map bounded to 200 (oldest dropped). The download also passes `requireAdmin`, so a ticket alone is worth nothing.
- **Limits**: ticket requests 5 per admin per minute, every attempt counted before the password is awaited and never given back (design 13.3 says "5 tickets per minute", so this is stricter than the user routes, which give a correct attempt back); starts 3 per admin per 10 minutes (B10); 3 concurrent downloads per process (429 `Retry-After: 5`).
- **Download**: name regex before any fs call; then ticket; then `openForDownload` (`O_NOFOLLOW`, regular-file `fstat`, lease so prune skips it, audits `backup.downloaded`); body is `Readable.toWeb(handle.createReadStream({highWaterMark: 64 KiB}))`; lease and slot are freed on stream close (finish, abort or cancel). Headers: `application/zip`, `Content-Disposition: attachment; filename="<name>"`, `Content-Length`, `Cache-Control: no-store`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`, `Accept-Ranges: none`; `Range` is never read (always 200). `app.ts` skips `compress()` for `/api/admin/backups/<name>` and uses a second `secureHeaders` instance with `no-referrer` for that path (secureHeaders overwrites a header set by the route). `HEAD` answers the headers and frees the lease.
- **Audit lines (stdout)**: `backup.created`/`backup.failed`/`backup.pruned` (service, actor = admin user id), `backup.ticket_issued {actor,name}`, `backup.ticket_denied {actor,name,reason}` with reason `wrong_password`, `rate_limited` or `invalid_ticket` (unknown, expired, reused or wrongly bound; the three are deliberately not told apart), `backup.downloaded {actor,name}`. Never the ticket, password, query or file contents (test greps the captured log).
- **Visibility sentinel**: not implicated. These routes return no campaign content (names, sizes, dates, versions, counts), and the zip is the admin's by design (design 10, B14); covered by the admin-only tests instead.
- **No delete route, no restore route** (tests: DELETE/PUT/PATCH/other POST paths are 404).

## Scheduled backups (Task M3.5, design 12, owner decision D9)

- **Off by default.** `BACKUP_EVERY_HOURS` (whole number 1 to 720; unset, empty or `0` = off). Anything else (`24h`, `1.5`, `721`, `-1`) makes the **server** refuse to start with `Refusing to start: BACKUP_EVERY_HOURS must be a whole number from 1 to 720, ...`; the command line is not blocked (`loadConfig` carries `backupEveryHoursError` and only `main.ts` acts on it), so a restore still works with a typo in the environment. `BACKUP_KEEP` is unchanged.
- **Code**: `src/services/backup-scheduler.ts` (`BackupScheduler`), built in `createServices` (`services.backupScheduler`), started by `main.ts` after the server listens (so after indexing). It only calls `BackupService.create({ actor: 'scheduler', trigger: 'scheduler' })`, which takes the existing in-process mutex and `.lock`, runs the free-space preflight and prunes with `prune(BACKUP_KEEP, 'scheduler')`. No retention rule, no endpoint, no cron library.
- **What counts as "the last backup"**: the newest backup file by the timestamp in its NAME, of ANY trigger (design: "the newest backup's timestamp"). A manual or CLI backup therefore postpones the next scheduled run, and a restart does not reset the schedule. Names later than the clock (clock stepped back) are ignored.
- **Timing**: next run = newest + interval. Nothing recent at start (older than the interval, or no backup at all) = ONE catch-up after 60 s plus 0 to 30 s of jitter, re-checked when it fires (a backup made meanwhile cancels it); missed runs are never replayed. A chain of unref'd `setTimeout`s, each at most 30 minutes long (Node's limit is 24.8 days, 720 h is 30), re-deriving the due time from the clock on every wake-up: a suspend or forward clock jump runs once, a backward jump (further away than any plan can be) recounts the interval from now.
- **Skips, never queues**: backup already running (this process or the CLI's lock), or the restore marker exists: one log line per state change, looked at again after 5 minutes (re-deriving from the list, so a manual backup that finished in the meantime cancels the run).
- **Failure**: the service audits `backup.failed` (`actor: 'scheduler'`, `trigger: 'scheduler'`, short reason) and keeps the fixed sentence for the admin page (`lastError`, the existing `FAILURE_TEXT`); nothing is pruned. The scheduler logs one fixed line without error text. Retries back off: 15 minutes, then x4 (1 h, 4 h, 16 h), never longer than the interval; a success resets it.
- **Shutdown**: (superseded by M3.7, see below: the handlers are always installed.) No new run after a stop signal, a running backup gets up to 8 s to finish. An interrupted backup publishes nothing (written aside, removed at the next start). All timers are unref'd.
- **Admin page**: `GET /api/admin/backups` gained `schedule: { everyHours, nextRunAt } | null` (additive, `packages/shared`), shown as one line under the intro: `Scheduled backups: off` or `Scheduled backups: every N hours, next run <time>`. No other page change.
- **Tests**: `test/backup-scheduler.test.ts` (33, injected clock and timer queue, no real waits; real `BackupService` for the manifest, list, prune and audit cases), one route test, one page spec. 15 mutations of the guards (overlap, marker, due re-check, unref, backoff hold and cap and reset, stop clearing, no re-arm after stop, trigger, actor, 30-minute chunks, clock-back, future names, busy skip) all fail a test.
- **For the M3.6 guide**: enable it with `BACKUP_EVERY_HOURS=24` (it protects against the passive flood case of D1); the first backup after a fresh start or downtime comes about 1 to 1.5 minutes after the server starts; a failing schedule shows on the Backups page and in the log as `backup.failed`; scheduled backups are on the same disk as the data unless `BACKUP_DIR` points elsewhere.

Before the server listens (indexing) a signal exits at once (143 / 130). - **History panel (Task N1.4, design in `docs/design/history-ui.md`):** GM only. A **History** button in the editor toolbar (hidden while previewing as a player) opens a panel under the page content (`campaign/history-panel.ts` + `.html`, lazy through `@defer`, OnPush, signals). Versions are listed newest first (who, source, time, cause, size, renames), 50 per page with **Load older versions**; tick one version to compare it with the current page, two to compare them. The text diff (`campaign/history-diff.ts`, pure, with a spec: line diff, word diff inside paired lines, collapsing of unchanged runs, list of other changed fields) marks changes by `+`/`-` gutter, underline and strike-through plus `added:`/`removed:` words for screen readers. **Restore** has no confirm; it saves pending editor edits first, replaces the page in place, and shows **Undo restore** (a second restore of the previously newest version), `restored: false` and warnings. A 409 loads the newer page, keeps the target ticked and asks the GM to look again (no retry). Snapshots stay in component memory and are dropped on close. **Race rules:** before a restore the panel saves pending edits through the editor, then reads the newest row with its own `GET ?limit=1` (never from the shared list, which a save-triggered reload can supersede); Undo targets that row, and there is no Undo when it could not be read. While a restore is writing the editor holds its debounced autosave back; a save that hits a 409 keeps its unsent changes in `pending`. If typing is pending or being saved when the restored (or newer) page arrives, the editor refuses it (`adoptHistory` returns false), keeps the typing under the conflict banner, and the panel says so ("Your unsaved typing was kept and was not saved. Reload the page...") with no Undo. Revoked tokens are soft-revoked and keep their name, so an AI-assistant row always shows the token name (the list DTO has no revoked flag, so there is no `(revoked)` suffix and the `(deleted token)` label is unreachable). A change too large to diff line by line shows "Large change, shown as a block." Tests: `history-diff.spec.ts`, `history-panel.spec.ts`, `e2e/history.spec.ts`. No server change: the 409 body carries the page at `details.current` and list rows carry `author`.
- **Endpoints (Task N1.3):** under `/api/campaigns/:cid/pages/:pid`, GM only (owner and co-DM, checked per request): `GET /history?before=&limit=` (`{ items }`, newest first, no content, `limit` 1 to 100), `GET /history/:rev` (full snapshot), `POST /history/:rev/restore` with `{ revision: <current page revision> }` (409 with the current page when stale; returns `{ page, restored, warnings }`; `restored: false` and no new row when the content is already live). Tests: `page-history.test.ts` (endpoints, 409, co-DM and demoted co-DM, removed member keeps no access) and the sentinel crawl in `visibility.test.ts` (a sentinel seeded in a DM-only block and property, edited away, all three routes refused for a player; since N1.5 the three routes are on the MCP allowlist, GM only).

## Trash endpoints (Task M4.1)

- `GET /api/campaigns/:cid/trash` (GM only, 403 for players): `{ items: [{ id, title, type, icon, subpageCount, deletedAt }] }`, newest first. An item is a deleted tree root (a deleted page whose parent was not deleted at the same moment); `subpageCount` counts the descendants deleted with it. A subpage deleted earlier than its parent is its own entry. No page bodies.
- `DELETE /api/campaigns/:cid/pages/:pid/purge` (GM only): permanently deletes a trashed page and the subpages deleted with it, answers `{ purged: [ids] }`. 404 for an unknown page (or one of another campaign), 400 "Only a deleted page can be purged" for a live page. Audit line `page.purged`.
- Purge removes the page rows and (by foreign key) tags, viewers, facets, outgoing links, entity references, property values, template usage and loot awards; incoming `page_links` rows and the search rows are deleted explicitly. Inventory and facet page references become null. Uploads belong to the campaign, not to a page, so purge never touches them: images stay valid for every page still showing them.
- Automatic purge (`src/services/trash-purger.ts`): pages deleted more than 30 days ago are removed 60 s after server start and then daily (unref'd `setTimeout` chain). It defers (re-check after 5 min) while `BackupService.isRunning()` or a restore marker exists, and is stopped by the clean shutdown (`stopScheduler` in `main.ts`). It logs one line when it purged something.
- `POST /pages/:pid/restore` (unchanged, verified by tests): brings back the subpages deleted with the page, rebuilds links, references and the search row; backlinks from other pages survive because their link rows are kept while a page is in the trash. If the parent is still deleted the page returns at the top level.
- MCP: `GET /campaigns/:cid/trash` is on the allowlist and exposed as the read tool `list_trash` (a player's token gets the route's 403 as a tool error). Purge stays off the allowlist (tested).
- UI: see "Trash view and undo (Task M4.3)" below.
- Co-DMs may view, restore and purge the trash (the same `requireDm` rule as the other DM-only routes). Owner decision.
- `encounters.locationPageId` and the page ids inside an encounter's creature JSON have no foreign key, so they may point at a purged page (same as after a soft delete).
- The purger skips a pass, with a log line, when the system clock is more than 10 minutes behind the newest page change or its own last run.

## Templates restore (Task M4.2)

- `GET /api/templates/trash[?campaignId=]`: `{ templates: [TemplateTrashItemDto] }` (a template summary plus `deletedAt`, no definition), newest deletion first. Lists only what the caller could edit: their own personal templates and the templates of campaigns they run as DM or co-DM (`?campaignId=` narrows to one campaign and drops personal ones). Built-ins never appear; players get an empty list.

Restore that one first." when a page template's parent is still deleted. Audit line `template.restored`.

- Names are not unique, so restoring has no name clash.

- Restore checks only the direct `extends` parent, not the whole chain (a deeper ancestor in the trash shows up in the restored template's `issues`).

## Template purge (Task M4.7)

- `DELETE /api/templates/:id/purge`: permanently deletes a trashed template the caller can edit (same rule as restore: owner for personal, DM or co-DM for campaign templates) and answers `{ purged: [id] }` (200). 400 "Only a deleted template can be purged" for a live template the caller can edit; 404 for unknown, not-editable (players, strangers, other campaigns) and built-in templates (ids do not leak; 401 anonymous). Audit line `template.purged`.
- Removes the template row, its versions, its `template_usage` rows (no foreign key, deleted explicitly) and any `campaign_template_defaults` rows; no schema change, so SQLite and the pg mirror are unchanged. Pages created from it keep their content and get `from_template_id`/`from_template_version` set to null. Linked block instances keep their content and stop following anything. A later save of such a page re-derives a usage row pointing at the purged id; it is harmless (nothing lists or propagates it).
- A child page template that `extends` a purged template is not blocked and not changed: it still loads, and its `issues` report that the parent was not found (same as for a trashed parent); it can be edited. Creating pages from it fails with the existing "template to extend" error until it is edited. Restoring a trashed child whose parent was purged is allowed.
- `TrashPurger` also purges templates deleted more than 30 days ago (same cutoff, deferral during backups and restores, clock check which now also considers the newest template change). `runOnce()` returns pages plus templates purged and logs one line for each kind. Built-ins are never purged.
- An edit of such a child that keeps the dangling `extendsRef` fails with 400 "The template to extend was not found", so the user must pick another parent or clear it in the same save (the M4.6 UI must handle this).
- The purger runs pages and templates in separate try/catch blocks: if one kind throws, the failure is logged ("... trying again tomorrow"), the other kind still runs, `runOnce()` returns the partial count and `lastRunFailed` is true; both are retried at the next daily run. `purgeIds` selects the eligible ids (deleted, not built-in, and past the cutoff when scheduled) inside its transaction and applies every delete only to those. The audit line `template.purged` carries `templateId, scope, campaignId, actor`.
- MCP: `GET /api/templates` and `GET /api/templates/:id` stay allowed, but the ids `trash` and `export` (and any id with whitespace or control characters) no longer match, so `get_template({ templateId: "trash" })` cannot reach the trash list. Purge and restore stay off the allowlist.

## Browser tests in CI (Task M5.3, decision D4)

`.github/workflows/e2e.yml` runs `pnpm e2e` on pull requests and by hand. **It is inactive until the owner registers a self-hosted runner**: with no runner carrying the labels, the job only queues.

- **Who runs**: only pull requests whose head repository is this repository (`head.repo.full_name == github.repository`); fork PRs are skipped. The trigger is `pull_request`, never `pull_request_target`. Permissions: `contents: read`; checkout uses `persist-credentials: false`; actions pinned by SHA (same as `ci.yml`); `timeout-minutes: 20`; one run per PR (`concurrency`, older runs cancelled).
- **No data leaves the runner**: no `upload-artifact`, no cache. The workflow sets `E2E_NO_ARTIFACTS=1`; `playwright.config.ts` then turns tracing and the HTML report off, uses `e2e/ci-reporter.ts` (prints only test title, status and duration; a failure shows file:line and the title, never error text, DOM or call log; rerun locally to see why), drops the server's stdout and stderr, and `api()` in `e2e/support.ts` leaves response bodies out of assertion messages. Video is off. A failing shared-page test still attaches a screenshot (`afterEach` in `e2e/support.ts`) and Playwright writes error context into `test-results/`: these exist only on the runner and the `always()` step deletes `playwright-report`, `test-results`, `e2e/.auth`, `blob-report` and the `cn-e2e-*` temp data folders. Local runs are unchanged (trace on failure, HTML report, full messages).
- **Trust warning (same-repository PRs and `workflow_dispatch`)**: a PR from a branch of this repository runs ITS OWN copy of the workflow, `playwright.config.ts`, the specs and `package.json` scripts on the runner, with the clone readable. Anyone who can push a branch (a collaborator, a compromised account, a Dependabot PR, which also runs) can therefore read or exfiltrate the 5etools data. Use the runner only for a **private** repository, never a public one. Run it ephemeral (a fresh VM or container per job) as an unprivileged user, mount the clone read-only, keep write access to the repository to people you trust, and protect `main` with branch protection; better, attach the job to an Environment with required reviewers so each run needs approval.
- **The 5etools clone** is read in place, never copied or committed: set `FIVETOOLS_SRC_PATH` to the absolute path of the runner's `5etools-src` clone (a first step fails the job when it is unset, relative or has no `data/` folder). `FIVETOOLS_IMG_PATH` is optional (the tests need no images).

### Registering the runner (owner)

1. On a machine you control (Linux, Google Chrome or Chromium): repository Settings > Actions > Runners > New self-hosted runner, and follow the steps. Give it the labels `self-hosted`, `linux`, `5etools` (the first two are automatic; add `5etools` when configuring). Run it as an unprivileged user, ideally in a VM or container, never as root.
2. Put the data on it once: shallow-clone `https://github.com/5etools-mirror-3/5etools-src.git` to e.g. `/opt/5etools/5etools-src`, and pull there now and then.
3. In the runner folder create a `.env` file (the runner loads it at start) with `FIVETOOLS_SRC_PATH=/opt/5etools/5etools-src` and, if Chrome is not at `/opt/google/chrome/chrome`, `CHROME_PATH=/usr/bin/chromium`. Restart the runner.
4. Settings > Actions > General > "Fork pull request workflows from outside collaborators": choose **Require approval for all outside collaborators**. A self-hosted runner must never run fork PRs (they could run code on your machine and read the clone); the workflow condition is a second barrier, not the only one. Only trusted people should be able to push branches to this repository.
5. Check: Actions > E2E > Run workflow on a branch. A green run proves the labels, the path and Chrome.

Notes: the desktop suite uses exactly the 8 sign-ups per minute the server allows (M4.5 caveat); a new spec that registers another person must share a user or the suite goes red here. The phone project runs on its own second server and has its own budget (Task M6.5). The runner keeps its workspace between runs, which is why the cleanup step exists.
